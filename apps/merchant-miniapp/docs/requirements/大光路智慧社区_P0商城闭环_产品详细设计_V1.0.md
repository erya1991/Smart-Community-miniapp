# 1. 需求背景与范围

## 1.1 建设背景

大光路智慧社区数字化运营平台的居民端不是独立商城，而是面向社区居民的统一数字化入口。商城是当前最高优先级业务闭环，也是后续社区服务共用商户、会员、支付、退款、评价和资金能力的基础。

技术底座已由原 RuoYi-Vue-Pro 方案调整为 LiLiShop。P0 不重新建设成熟电商内核，优先复用 LiLiShop 已有的多商户、商品、SKU、库存、购物车、交易、订单、支付、售后、评价、店铺和商家权限能力，重点补充大光路实际运营所需的商户合作关系、经营资格、社区履约和微信分账能力。

## 1.2 P0 目标

P0 完成后，应能够形成真实可运行的商城闭环：

```text
商户申请入驻
→ 平台审核
→ 建立合作协议与经营资格
→ 商户维护商品
→ 平台审核商品
→ 商品上架
→ 居民浏览、加购、下单
→ 微信支付
→ 商户备货与履约
→ 居民收货 / 自提 / 到店核销
→ 订单完成
→ 平台佣金计算与微信分账
→ 售后、退款及必要的分账回退
→ 评价
```

商城是否完成不以页面数量为标准，而以上述链路能够在三个端真实走通并留下完整业务记录为标准。

## 1.3 本期范围

P0 包含：

- 管理后台基础账号、角色和商城所需权限；
- 商户入驻、审核、商户/店铺资料；
- 轻量合作协议；
- 商户经营资格；
- 商品、SKU、价格、库存、商品审核和上下架；
- 住户商城浏览、购物车、确认订单、地址、支付、订单；
- 商户配送、社区自提、到店核销和普通物流的最小履约能力；
- 售后、退款、评价；
- 平台佣金、分账规则、分账接收方、分账执行、异常和回退；
- 商户端资金结果查询；
- 商城闭环所需的消息与待办。

## 1.4 本期不建设

P0 明确不包含：

- 完整 Project 项目管理、项目切换和项目级数据隔离；
- 社区服务预约与服务订单；
- 物业缴费、房屋绑定、居民共享、邻里互助、停车缴费；
- 社区团购、拼团、秒杀等营销玩法；
- 骑手平台、路线规划、实时定位和运力调度；
- 复杂仓储、供应链、采购；
- 商户钱包、自动提现、财务总账；
- 多级分账和复杂清结算；
- 积分商城、会员等级等复杂会员体系；
- 为多项目场景提前大范围改造 LiLiShop 核心表。

## 1.5 项目管理处理原则

P0 按“大光路单项目”运行，不建设项目列表、项目切换器和项目权限。

新增的合作协议、分账规则等扩展对象可预留未来项目关联能力，但商品、订单等 LiLiShop 核心对象本期不强制增加 `projectId`。

后续需要同时运营多个社区时，再单独进行多项目化改造。

# 2. 整体业务设计

## 2.1 三端定位

| 产品端 | 核心用户 | P0 定位 |
|---|---|---|
| 管理后台 Web | 平台运营、审核人员、财务、管理员 | 管准入、管审核、管规则、管资金、管异常、看全局 |
| 住户小程序 | 社区居民 | 智慧社区统一入口中的商城消费端，前端重新开发，后端复用 LiLiShop buyer 相关能力 |
| 商户小程序 | 商户负责人、工作人员 | 商户移动经营主端，管理商品、订单、履约、售后和资金结果，后端优先复用 seller-api |

LiLiShop 原有买家端和 Seller Web 可作为业务、字段和交互参考，但不作为大光路两个小程序的界面基线。

## 2.2 角色设计

| 角色 | 主要职责 | 主要端 |
|---|---|---|
| 居民 | 浏览商品、下单、支付、收货、自提/核销、售后、评价 | 住户小程序 |
| 商户负责人 | 入驻申请、查看合作状态、商品经营、订单履约、售后处理、资金查看 | 商户小程序 |
| 商户工作人员 | 商品、订单、履约等授权范围内操作 | 商户小程序 |
| 平台运营人员 | 商户、商品、订单日常管理 | Web |
| 平台审核人员 | 入驻审核、商品审核 | Web |
| 平台财务/资金人员 | 分账规则、接收方、分账异常、基础对账 | Web |
| 系统管理员 | 账号、角色、基础配置及最高权限 | Web |

P0 不单独建设运营作业小程序。

## 2.3 核心业务对象与 LiLiShop 复用关系

| 业务对象 | 处理方式 | P0 说明 |

| Member / MemberAddress | 直接复用 | 居民身份和收货地址 |

| Clerk / Role / Department | 精简复用 | 商户人员和权限 |
| StoreAddress | 改造复用 | 自提点/核销点基础 |
| Goods / GoodsSku | 直接复用 | 商品、规格、价格、库存 |
| Cart / Trade / Order / OrderItem | 直接复用为主 | 购物车、交易、店铺订单 |
| Payment / Refund | 直接复用为主 | 微信支付和退款 |
| AfterSale | 直接复用 | 售后主流程 |
| Evaluation | 直接复用 | 商品评价 |
| StoreFlow | 改造复用 | 商户订单流水、平台佣金、商户应得金额基础 |
| CooperationAgreement | 新增 | 轻量合作协议 |
| 商户经营资格聚合 | 新增业务规则 | 由商户状态、资质、协议、支付/分账状态综合计算 |
| 社区履约扩展记录 | 视实现需要轻量新增 | 仅保存 LiLiShop 主订单状态无法表达的备货、商户配送等子状态 |
| ProfitSharingRule | 新增 | 分账规则及版本 |
| ProfitSharingReceiver | 新增 | 微信分账接收方 |
| ProfitSharingOrder / Detail | 新增 | 分账请求和接收方结果 |
| ProfitSharingReturn | 新增 | 已分账后的分账回退 |

## 2.4 LiLiShop 当前能力基线

P0 设计遵循 LiLiShop 当前已有状态和模型，不重新设计第二套商城状态机。

### 商户/店铺状态

LiLiShop `StoreStatusEnum` 已包含：

- APPLY：申请开店；
- APPLYING：申请中；
- REFUSED：审核拒绝；
- OPEN：开启中；
- CLOSED：店铺关闭。

大光路在此基础上增加“经营资格/交易资格”的业务聚合，不额外替代 Store 主状态。

### 商品状态

商品审核使用：

- TOBEAUDITED：待审核；
- PASS：审核通过；
- REFUSE：审核拒绝。

商品上下架使用：

- UPPER：上架；
- DOWN：下架。

### 订单状态

LiLiShop `OrderStatusEnum` 已包含：

- UNPAID：未付款；
- PAID：已付款；
- UNDELIVERED：待发货；
- PARTS_DELIVERED：部分发货；
- DELIVERED：已发货；
- STAY_PICKED_UP：待自提；
- TAKE：待核验；
- COMPLETED：已完成；
- CANCELLED：已关闭。

P0 原则上不修改该主状态枚举。大光路“备货、待配送、配送中”等通过履约子状态或展示状态补充。

### 配送方式

LiLiShop 当前配送方式包括：

- SELF_PICK_UP：自提；
- LOCAL_TOWN_DELIVERY：同城配送；
- LOGISTICS：物流；
- VIRTUAL：虚拟发货。

P0 映射：

| 大光路场景 | LiLiShop 基础方式 | 处理原则 |
|---|---|---|
| 商户配送 | LOCAL_TOWN_DELIVERY | 复用类型，补地址快照和轻量履约子状态 |
| 社区自提 | SELF_PICK_UP | 复用 StoreAddress、自提码/核销能力 |
| 到店核销 | SELF_PICK_UP 为主 | 使用门店自提点 + 核销码；如需区分场景，只做轻量扩展 |
| 普通物流 | LOGISTICS | 保留原生能力，不作为 P0 重点 |

### 售后状态

LiLiShop 售后主状态包括申请中、已通过、已拒绝、待卖家收货、卖家确认收货、卖家终止、买家取消、等待平台退款、完成；售后类型包括退款、退货。

P0 直接沿用，不重新建设第二套售后状态机。

## 2.5 P0 核心业务流程

### 2.5.1 商户准入与供给流程

```text
商户小程序填写入驻申请
→ 保存草稿
→ 提交审核
→ Web 审核通过/驳回
→ Store 开启
→ 平台建立合作协议
→ 系统计算经营基础资格
→ 商户维护商品
→ 提交商品审核
→ Web 审核
→ 满足正式交易资格后商品可上架经营
```

### 2.5.2 居民交易与履约流程

```text
居民进入商城
→ 浏览商品/选择 SKU
→ 加入购物车或立即购买
→ 确认订单
→ 选择履约方式
→ 微信支付
→ 商户处理订单
→ 商户配送 / 社区自提 / 到店核销 / 普通物流
→ 居民确认收货或核销完成
→ 订单完成
```

### 2.5.3 资金流程

```text
订单支付成功
→ 形成订单资金记录和 StoreFlow
→ 保存订单对应的分账规则快照
→ 订单完成
→ 计算平台佣金与商户应得
→ 创建分账单
→ 调用微信分账
→ 查询最终结果
→ 成功后更新资金状态
→ 商户端可查看最终结果
```

### 2.5.4 售后退款流程

```text
居民申请退款/退货
→ 商户处理
→ 判断订单是否已分账
→ 未分账：进入正常退款
→ 已分账：先按规则发起分账回退
→ 微信退款
→ 更新售后、订单和资金状态
```

## 2.6 P0 关键设计原则

1. **不重写商城内核。** Goods、GoodsSku、Trade、Order、AfterSale、Payment 等核心模型优先原样复用。
2. **前端可以重做，业务内核不重复建设。** 住户小程序重新开发 UI 和信息架构，商户小程序修改现有原型，但两端都优先使用现有 buyer/seller 后端能力。
3. **不为了“社区化”修改所有订单状态。** 社区履约差异优先通过扩展状态和展示状态解决。
4. **商户准入与交易资格分层。** 商户审核通过后可以提前维护商品；支付/分账未就绪时不得正式交易。
5. **资金状态独立于订单状态。** 订单完成不等于分账完成。
6. **历史快照不可被后续规则修改影响。** 商品、价格、地址、佣金/分账规则等关键交易数据必须以订单快照为准。
7. **P0 先保证闭环，再开放 LiLiShop 的更多商城能力。** 营销、复杂统计等不作为上线前置。

# 4. 功能详细设计

## 4.1 入驻申请（商户小程序）

### 4.1.1 功能概述

商户负责人通过商户小程序提交开店申请。优先复用 LiLiShop Store / StoreDetail 申请流程，不再新建第二套商户申请主体。

### 4.1.2 业务流程

```text
未申请
→ 填写申请草稿
→ 提交
→ 申请中
→ 审核通过 / 审核驳回
→ 驳回后修改重新提交
```

对应 Store 主状态优先使用 APPLY、APPLYING、REFUSED、OPEN。

### 4.1.3 申请信息

商户端按移动端体验分步填写：

**第一步：经营主体**

- 主体名称；
- 主体类型：企业/机构、个体工商户；
- 营业执照号；
- 营业执照图片；
- 法定经营范围；
- 法人/经营者姓名；
- 法人/经营者证件信息及必要附件。

**第二步：联系人**

- 联系人姓名；
- 联系手机号；
- 电子邮箱（非必填）。

**第三步：店铺信息**

- 店铺名称；
- 店铺 Logo；
- 店铺简介；
- 店铺地址；
- 经纬度；
- 经营类目；
- 联系电话。

**第四步：其他资料**

- 平台要求的必要补充资质；
- 其他附件。

LiLiShop `StoreDetail` 当前存在结算银行等字段。P0 产品要求遵循“实际运营需要”原则：若最终资金方案不要求商户在入驻阶段填写该信息，应在二开中调整接口条件必填规则，不为了复用原接口强制商户填写无实际用途的信息。

### 4.1.4 业务规则

- 商户小程序当前登录人员作为申请负责人；
- 同一主体重复申请时需提示已有申请/店铺，避免重复创建；
- 草稿可多次保存；
- 申请中不得直接修改核心主体资料，需撤回能力时优先复用现有机制，否则由平台驳回后修改；
- 驳回必须显示平台原因；
- 审核通过只代表 Store 已开通，不自动代表可以正式交易；
- 审核通过后可进入商品准备阶段。

### 4.1.5 页面与交互

现有商户小程序入驻原型保留分步结构，但需：

- 删除“项目邀请/项目经营授权”等 P0 不再实施内容；
- 字段改为与 Store / StoreDetail 实际可复用字段一致；

## 4.3 合作协议与经营资格（Web / 商户小程序）

### 4.3.1 功能概述

P0 不建设完整合同系统，只新增轻量合作协议，并通过协议等条件计算商户是否具备正式经营/交易资格。

### 4.3.2 合作协议字段

| 字段 | 规则 |
|---|---|
| 协议编号 | 必填，全局唯一 |
| 协议名称 | 必填 |
| 关联商户/店铺 | 必填 |
| 协议版本 | 必填 |
| 生效日期 | 必填 |
| 失效日期 | 可为空，空表示长期或按规则处理 |
| 协议附件 | 必填或按实际运营要求配置 |
| 经营范围/类目摘要 | S0 |
| 平台服务费/佣金规则引用 | S0 |
| 售后/退款约定摘要 | S1 |
| 状态 | 草稿/生效/失效/终止 |
| 备注 | 非必填 |

P0 不再关联 Project。

### 4.3.3 经营资格分层

为避免支付接入阻塞商品准备，经营资格分为两层：

**经营基础资格**

```text
Store 审核通过并开启
+ 必要资质有效
+ 合作协议有效
= 经营基础资格 READY
```

经营基础资格 READY 后，商户可新增/编辑商品并提交审核。

**正式交易资格**

```text
经营基础资格 READY
+ 微信支付满足交易要求
+ 需分账商户的分账关系满足要求
= 正式交易资格 READY
```

正式交易资格 READY 后，商品才允许正式上架并接受居民新订单。

### 4.3.4 商户端展示

商户小程序只显示结果和原因，不允许修改协议和平台规则：

- 商户审核：已通过/未通过；
- 资质：正常/待完善；
- 合作协议：有效/未建立/已失效；
- 支付接入：可用/待配置；
- 分账接入：可用/待配置/异常；
- 最终状态：可维护商品 / 可正式交易 / 暂停经营。

### 4.3.5 联动规则

- 协议失效后禁止新交易，不影响历史订单履约、退款、分账；
- 已审核商品不因协议失效被删除；
- 商户恢复资格后，可重新上架符合条件商品；
- 资格校验必须在后端执行，不能只靠前端按钮隐藏。

- 复杂优惠券配置；
- 分销；
- 直播；

已有 Web/Seller 能力不强制删除，但不作为商户小程序 P0 开发范围。

## 4.10 确认订单、地址与履约方式（住户小程序）

### 4.10.1 页面内容

### 4.10.2 履约方式

#### 商户配送

展示名称：“商户配送”。

后端基础映射：`LOCAL_TOWN_DELIVERY`。

要求：

- 居民必须选择收货地址；
- 订单必须保存姓名、手机号和地址快照；
- 商户可查看配送地址和联系方式；
- P0 不计算骑手、轨迹和智能运力。

LiLiShop 当前订单构造逻辑对 LOGISTICS 有明确地址快照处理，因此 `LOCAL_TOWN_DELIVERY` 场景在二开时必须专项核对并保证地址快照完整保存，不能只改前端配送方式文案。

#### 社区自提

后端基础映射：`SELF_PICK_UP`。

- 居民选择商户可用自提点；
- 自提点优先复用 `StoreAddress`；
- 展示自提点名称、地址、电话；
- 支付后形成提货/核销凭证；
- 商户核销后完成相应履约。

#### 到店核销

P0 不单独重建一套虚拟商品订单。

建议同样复用 `SELF_PICK_UP + StoreAddress + verificationCode`：

- 将门店本身配置为“到店核销点”；
- 如后端需要区分“社区自提点”和“到店核销点”，仅增加轻量点位类型扩展；
- 居民支付后展示核销码；
- 商户扫码/输码核销。

#### 普通物流

复用 `LOGISTICS`，P0 保留但非重点。

### 4.10.3 自提点管理

优先复用 LiLiShop `StoreAddress`：

- 自提点名称；
- 地址；
- 经纬度；
- 联系电话。

自提点维护可以保留在 LiLiShop Seller Web 或后续补到商户小程序；P0 商户小程序若时间紧张，至少保证商户可选择已有自提点进行订单履约。

## 4.11 微信支付（住户小程序）

- 订单超时关闭优先使用 LiLiShop 原机制；

- 配送中；
- 待自提/待核销；
- 已完成；
- 售后中。

这是商户视角聚合状态，不替换 LiLiShop 主订单状态。

### 4.13.2 订单详情

展示：

- 订单编号；
- 居民联系人；
- 地址（需要配送时）；
- 商品/SKU/数量；
- 应付金额；
- 履约方式；
- 买家备注；
- 当前订单状态；
- 售后状态；
- 可执行操作。

商户只能看到本店订单。

### 4.13.3 商户配送流程

P0 推荐业务展示：

```text
已支付/待处理
→ 开始备货
→ 备货完成/待配送
→ 开始配送
→ 配送中
→ 确认送达
→ 等待居民确认收货或按平台规则完成
```

实现原则：

- 不为上述每一步增加新的 `OrderStatusEnum`；
- `UNDELIVERED / DELIVERED / RECEIVED` 等主状态继续由 LiLiShop 管理；
- PREPARING、WAIT_DELIVERY、DELIVERING 等只作为履约扩展/商户操作状态；
- 每次关键履约操作记录操作人和时间；
- “确认送达”不等于微信分账成功。

### 4.13.4 社区自提

```text
支付成功
→ 商户备货
→ 备货完成
→ 待自提
→ 居民出示提货码
→ 商户核销
→ 完成
```

优先复用 `STAY_PICKED_UP`、`verificationCode` 和 `StoreAddress`。

### 4.13.5 到店核销

与社区自提共享核销底层能力，业务展示区分“到店核销”。

商户操作：

- 扫码或输入核销码；
- 校验订单属于本店；
- 校验订单未核销、未关闭、无阻断性售后；
- 成功后记录核销人员、时间和点位；
- 核销接口必须幂等，重复核销提示“已核销”。

### 4.13.6 普通物流

原生 LOGISTICS 能力可继续使用，包括物流公司、物流单号等；P0 不重点改造。

# 5. 跨功能业务规则

## 5.1 商户资格统一规则

商户资格不得分散在多个页面各算一套。

建议统一返回：

- `storeStatus`：LiLiShop 店铺状态；
- `baseBusinessReady`：经营基础资格；
- `tradeReady`：正式交易资格；
- `reasonCodes/reasons`：不可经营原因。

商品提交、上架、居民下单等关键动作统一调用同一资格判断。

## 5.2 商品可售规则

商品面向居民可售必须同时满足：

```text
商品审核 PASS
+ 商品状态 UPPER
+ SKU 有效且库存满足
+ Store OPEN
+ 正式交易资格 READY
```

## 5.3 订单快照规则

订单创建后至少固化：

- 商品名称、图片、SKU 和规格；
- 成交单价；
- 数量；
- 店铺信息；
- 居民收货信息/自提点信息；
- 履约方式；
- 金额明细；
- 与分账计算相关的规则版本和关键比例。

商品、地址、合作协议后续修改不得覆盖历史订单快照。

## 5.4 履约方式统一规则

商城前端统一使用用户语言：

- 商户配送；
- 社区自提；
- 到店核销；
- 普通物流。

后端以 LiLiShop DeliveryMethod 为基础，不要求前端直接展示枚举英文值。

## 5.5 订单状态与履约状态分离

OrderStatus 继续作为主状态。

社区差异流程使用履约展示/扩展状态，不通过频繁增加订单枚举解决。

例如：

```text
OrderStatus = UNDELIVERED
FulfillmentStatus = PREPARING / WAIT_DELIVERY / DELIVERING
```

## 5.6 支付、订单、分账三套状态不得混用

- 支付成功：只代表钱已支付；
- 订单完成：只代表业务履约完成；
- 分账成功：只代表资金分配成功。

三个事实必须分别记录。

## 5.7 退款与分账联动

退款操作必须先确认当前资金状态：

- 未分账：直接按退款能力处理；
- 分账处理中：先查询最终结果，禁止盲目退款；
- 已分账：按第三方能力先完成必要回退；
- 分账/回退失败：进入资金异常，不伪造退款完成状态。

## 5.8 数据权限

- 居民仅查看自己的订单、售后和评价；
- 商户仅查看本店商品、订单、售后和资金；
- 平台角色按菜单和按钮权限访问全局数据；
- P0 不增加项目级数据权限。

## 5.9 幂等与防重复

以下操作必须具备幂等保障：

- 支付回调；
- 核销；
- 确认收货；
- 退款；
- 分账；
- 分账查询状态同步；
- 分账回退。

## 5.10 历史数据保留

商户关闭、协议终止、商品下架均不得删除历史交易数据。

历史订单仍需支持：

- 查看；
- 售后；
- 退款；
- 分账/回退；
- 对账。

- 项目经营授权；
- P1 社区服务相关入口可暂时隐藏或标记后续；
- P0 不实施的复杂经营功能。

### 重点修改

- 入驻申请字段；
- 审核进度；
- 合作协议/经营资格展示；
- 商品新增/编辑字段，特别是 SKU 编码、成本、重量；
- 商品审核和上下架状态；
- 订单状态和操作按钮；
- 商户配送履约；
- 自提/到店核销；
- 售后处理；
- 分账结果；
- 工作台待办。

## 7.3 管理后台 Web

Web 不重新做整套原型：

- LiLiShop 已成熟的商户、商品、订单、售后页面优先直接使用并做字段/品牌适配；
- 新增合作协议、经营资格、分账规则、分账接收方、分账记录与异常页面；
- 页面交互尽量遵循 LiLiShop Manager 原有组件和布局，降低研发成本。

# 8. P0 验收场景

## 8.1 商户准入与商品供给

**场景 A：商户首次入驻**

```text
提交申请
→ Web 审核通过
→ 建立合作协议
→ 经营基础资格 READY
→ 商户创建商品
→ 商品审核通过
→ 正式交易资格 READY
→ 商品上架
```

验收：居民可正常看到商品。

## 8.2 商户配送闭环

**场景 B：商户配送**

```text
居民下单支付
→ 商户备货
→ 待配送
→ 配送中
→ 确认送达
→ 居民确认收货
→ 订单完成
→ 分账成功
```

验收：订单状态、履约记录、支付记录、StoreFlow 和分账记录可相互关联。

## 8.3 社区自提闭环

**场景 C：社区自提**

```text
选择社区自提点
→ 支付
→ 商户备货
→ 待自提
→ 居民出示提货码
→ 商户核销
→ 完成
→ 分账
```

验收：核销重复操作不会重复完成订单。

## 8.4 到店核销闭环

**场景 D：到店核销**

```text
选择到店核销点
→ 支付
→ 生成核销凭证
→ 到店
→ 商户核销
→ 完成
→ 分账
```

验收：居民和商户端都能看到一致核销结果。

## 8.5 未分账退款

**场景 E：订单完成前退款**

```text
支付
→ 申请退款
→ 审核通过
→ 微信退款
→ 退款完成
```

验收：不得产生错误的已分账资金状态。

## 8.6 已分账退款

**场景 F：已分账后售后退款**

```text
订单完成
→ 分账成功
→ 发起售后退款
→ 分账回退
→ 微信退款
→ 最终完成
```

验收：分账、回退、退款三类记录完整且金额一致。

## 8.7 资格失效

**场景 G：合作协议失效/店铺关闭**

- 新商品不得正式上架；
- 居民不得创建新交易；
- 历史订单仍可查看、履约、售后、退款和处理分账。

## 8.8 三端一致性

同一订单在：

- 住户小程序；
- 商户小程序；
- 管理后台 Web

显示的核心订单状态、售后状态、履约结果必须来源于同一后端事实，允许展示语言不同，但不能出现业务矛盾。

# 9. P0 实施建议顺序

产品、研发、测试可并行，但研发主链路建议按以下顺序推进：

```text
第一批：LiLiShop 基线环境 + 三端登录/账号
    ↓
第二批：商户入驻、审核、合作协议、经营资格
    ↓
第三批：商品/SKU/库存 + 商品审核
    ↓
第四批：住户商城浏览 + 购物车 + 确认订单
    ↓
第五批：微信支付 + 我的订单
    ↓
第六批：商户配送 / 自提 / 核销履约
    ↓
第七批：售后、退款、评价
    ↓
第八批：分账规则、接收方、执行、回退、商户资金结果
    ↓
P0 全链路回归与真实资金验收
```

如果微信分账外部条件尚未完全就绪，前七批仍可先使用明确的资金抽象状态开发和联调，但 **P0 最终正式验收必须补齐真实微信支付、分账、回退/退款验证**。

# 11. 本版最终结论

1. **LiLiShop 商城内核继续作为 P0 唯一商城交易底座，不建设第二套 Goods/Order/Payment/AfterSale。**
2. **住户小程序重新开发商城前端，但直接复用 LiLiShop buyer 侧后端能力。**
3. **商户小程序保留现有原型框架，按 seller-api 和本设计修改字段、状态和操作。**
4. **管理后台以 LiLiShop Manager 现有页面为主，只新增大光路差异能力。**
5. **完整 Project 项目管理暂缓，P0 按单项目运行。**
6. **社区履约通过 LiLiShop 配送/自提能力 + 轻量扩展实现，不重写主订单状态机。**
7. **StoreFlow 继续作为商户资金计算和流水基础，但真实微信分账需独立新增可审计的规则、执行和回退对象。**
8. **P0 的最终完成标准是“准入→商品→交易→支付→履约→分账→退款/回退”真实闭环，而不是前端页面全部完成。**
