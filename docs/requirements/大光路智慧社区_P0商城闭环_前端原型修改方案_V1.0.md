# 1. 本轮原型调整总体原则

本轮只围绕 **P0 商城闭环** 修改原型，不同时展开社区服务详细原型，也不继续沿用已经暂缓的完整 Project 项目管理方案。

整体按以下顺序实施：

1. 住户小程序商城链路补齐；
2. 商户小程序商城经营与履约链路补齐；
3. Web 新增页面及既有 LiLiShop Manager 页面适配；
4. 三端统一检查同一订单、同一商户、同一售后和同一资金状态的展示一致性。

本轮不是重新设计第二套商城业务，而是把当前小程序原型调整到与 LiLiShop 实际商城模型一致。

## 1.1 原型处理标识

| 标识 | 含义 |
|---|---|
| 保留 | 页面结构和主要视觉继续使用，仅替换数据与少量文案 |
| 修改 | 保留现有页面，但需要调整模块、字段、状态或操作 |
| 新增 | 当前代码中没有该页面，需要新增页面 |
| 合并 | 两个现有页面职能重叠，P0 合并成一个入口/页面 |
| 隐藏 | P0 不开发，暂时从导航和入口隐藏，不删除后续设计资产 |
| 后移 | 进入 P1 社区服务或后续阶段 |

## 1.2 通用视觉原则

两端继续遵循现有：

- `MiniApp_Design_System_V1.1`；
- 微信小程序实现规范；
- 当前 AppNavbar / AppPage / AppTabbar / BaseCard / StatusTag 等公共组件；
- Stitch 视觉母版映射。

住户端仍以 **R｜Replica Mode** 为主，保持居民消费场景的完整视觉体验。

商户端：
- 高频列表、工作台继续使用 **O｜Operational Mode**；
- 表单、详情、核销、高风险操作使用 **R｜Replica Mode**。

## 1.3 P0 不再出现的界面概念

本轮页面中删除或停止扩展：

- 项目选择器；
- 项目邀请；
- 项目经营授权；
- 多项目经营状态；
- Project 维度统计；
- 社区服务商品/服务混合经营入口；
- “即将开放”的服务业务占位卡片，如会干扰 P0 商城验收则直接隐藏。

P0 默认当前系统只运营“大光路社区”单项目。

对于“社区”这一居民认知信息可以保留，例如首页展示“大光路社区”，但它只是当前社区标识，不提供切换功能，也不参与 Project 权限逻辑。

# 2. 住户小程序商城原型修改方案

## 2.1 当前原型判断

当前住户端实际代码页面主要为：

```text
首页
服务
商城
我的
```

当前商城页已经包含：

- 社区商城标题；
- 搜索框；
- 商品分类；
- 商品双列卡片；
- 购物车图标；
- 社区商品供应提示。

但当前商城仍属于展示型原型：

- 分类点击未形成真实列表页；
- 商品卡片没有商品详情链路；
- 购物车为不可用占位；
- 没有确认订单；
- 没有收货地址管理；
- 没有支付结果；
- 没有商城订单列表/详情；
- 没有售后链路；
- 没有评价页面。

因此住户端 P0 的核心不是推翻现有首页和商城视觉，而是：

> **保留智慧社区门户和现有商城视觉语言，补齐从商品浏览到订单、履约、售后的完整商城链路。**

# 3. 住户端详细页面修改

## 3.1 智慧社区首页｜修改

当前页面路径：

`pages/home/index`

### 保留

保留现有：

- “智慧社区平台”整体导航；
- Hero 区；
- 快捷入口卡片；
- 便民服务区；
- “社区好物”推荐区；
- 当前 TabBar。

### 删除/调整

当前顶部存在可点击的 `project-row` 和 Project Store。

P0 调整为：

```text
大光路社区
```

作为静态当前社区标识。

要求：

- 不显示下拉箭头；
- 不提供项目切换；
- 不再依赖 `useProjectStore()` 决定商城数据；
- 首页商品推荐不再按 Project mock 数据过滤。

### 商城入口调整

“社区好物”继续保留，但需要变成真实商城入口：

- “进入商城” → `/pages/mall/index`
- ProductCard 点击 → `/pages/mall/product-detail/index?id=xxx`
- 数据字段与商城商品统一；
- 只显示审核通过、已上架、可售商品。

### 首页不做的事情

不要把首页改成商城首页。

首页仍然服务于整个智慧社区，商城只是其中一个业务入口。

## 3.2 商城首页｜重点修改

当前页面：

`pages/mall/index`

当前视觉总体可保留。

### 页面顶部

当前结构：

```text
社区位置 + 购物车
搜索
分类
社区周边商户直供提示
社区精选
```

P0 调整为：

```text
社区商城标题
购物车入口
搜索入口
商品分类
推荐/最新商品
商品双列流
```

### 删除项目切换

当前：

```text
location + projectName + chevron
```

删除可点击项目切换。

可选择两种视觉处理：

**推荐：**

顶部只保留一行轻量说明：

```text
大光路社区 · 社区好物
```

不作为按钮。

### 购物车

当前购物车点击 `FeatureUnavailable`。

改为：

- 点击进入购物车；
- 显示购物车商品数量；
- 数量以购物车接口结果为准；
- 数量为 0 时不显示角标。

### 搜索

当前搜索框直接在 mock 商品中本地过滤。

P0 改为：

- 点击/提交关键词进入商品列表页；
- 商品列表页带 `keyword`；
- 后续对接 LiLiShop Search；
- 搜索框保留历史关键词能力属于 S1，可暂不做。

### 分类

当前分类点击不可用。

P0 改为：

- 点击类目进入商品列表；
- 商品列表带 `categoryId`；
- 分类只展示当前商城启用类目。

### 商品流

商品卡至少展示：

- 商品图；
- 商品名称；
- 卖点/简短描述；
- 销售价；
- 店铺名称；
- 销量/评价中至少保留接口稳定可提供的信息。

商品卡点击进入商品详情。

### 删除/弱化的展示

“社区周边商户直供 · 新鲜便捷”可以保留为品牌说明，但不能代替实际店铺和商品信息。

## 3.4 商品详情｜新增

建议路径：

`pages/mall/product-detail/index`

直接使用 Stitch B1-_2。

### 页面顺序

1. 商品图片轮播；
2. 价格；
3. 商品名称；
4. 卖点；
5. 销量/评价摘要；
6. SKU 选择；
7. 履约方式说明；
8. 店铺信息；
9. 商品详情；
10. 底部固定购买栏。

### 底部购买栏

建议：

```text
店铺
购物车
加入购物车
立即购买
```

P0 不增加收藏等非闭环能力。

### SKU 选择

点击 SKU 区弹出 Bottom Sheet：

- 规格组合；
- 当前价格；
- 当前库存；
- 数量。

规则：

- 未选齐规格禁止提交；
- 库存不足显示原因；
- 商品/店铺不可交易时禁用购买按钮。

### 履约提示

详情页只提示该商品/店铺支持哪些方式，例如：

```text
支持：商户配送 / 社区自提
```

真正的履约方式选择放到确认订单页。

## 3.5 购物车｜新增

建议路径：

`pages/mall/cart/index`

使用 Stitch B2-_9。

### 页面结构

按商户分组：

```text
商户A
  商品1
  商品2

商户B
  商品3
```

每个商品项：

- 勾选；
- 图片；
- 名称；
- SKU；
- 当前价；
- 数量；
- 失效提示。

### 底部

```text
全选
已选金额
结算
```

### 关键调整

当前 Stitch 映射中曾按“多商户分组独立结算”理解。

新版 P0 原则改为：

- UI 仍按店铺分组；
- 是否允许多店铺一起结算，遵循 LiLiShop 原生 Trade 能力；
- 不在前端人为创造“一订单一商户”限制；
- P0 原型至少完整表现单店铺结算场景。

## 3.8 确认订单｜重点新增

建议路径：

`pages/mall/checkout/index`

使用 Stitch B2-_8。

这是住户端 P0 最重要的页面之一。

### 页面结构

按顺序：

1. 履约方式；
2. 收货地址 / 自提点；
3. 店铺及商品；
4. 买家备注；
5. 金额汇总；
6. 底部应付金额 + 提交订单。

### 履约方式设计

使用用户语言：

- 商户配送；
- 社区自提；
- 到店核销；
- 普通物流。

仅显示当前订单实际支持的方式。

#### 商户配送

选中后：

- 显示收货地址；
- 必须选择地址；
- 显示联系人/电话。

#### 社区自提

选中后：

- 隐藏收货地址；
- 显示自提点选择；
- 自提点展示名称、地址、联系电话。

#### 到店核销

选中后：

- 显示到店核销点；
- 不展示物流地址；
- 文案强调支付后凭核销码到店使用。

#### 普通物流

使用标准地址和运费逻辑。

### 金额区

P0 必须：

- 商品金额；
- 运费；
- 应付金额。

已有 LiLiShop 优惠信息可以显示，但不作为原型主线。

# 16. 本轮原型修改的推荐实施顺序

综合研发依赖和原型成熟度，推荐：

```text
第一批：住户商城 浏览链路
首页 → 商城首页 → 商品列表 → 商品详情

第二批：商户 商品供给链路
入驻/资格收口 → 工作台 → 商品列表 → 商品编辑/SKU

第三批：住户 下单支付链路
购物车 → 地址 → 确认订单 → 支付结果

第四批：商户 履约链路
订单列表 → 订单详情 → 商户配送 → 核销

第五批：住户 订单链路
我的订单 → 订单详情 → 自提/核销展示

第六批：三端 售后
居民售后 → 商户处理 → Web监管

第七批：资金
Web 分账规则/接收方/记录 → 商户资金结果

第八批：评价及 P0 UI 收口
```

这样做的好处是：

- 不需要等全部页面设计结束才开始研发；
- 住户和商户原型可以交叉推进；
- 每一批都对应一个可以测试的业务段；
- 优先把商城核心链路做完整，而不是先补大量管理页面。

# 19. 本轮结论

住户端：

> 保留智慧社区整体入口和视觉体系，商城前端重新补齐真实交易页面，不复制 LiLiShop uni-app UI，但接口和数据模型按 LiLiShop buyer-api 对齐。

商户端：

> 不推倒当前原型，保留工作台、经营、订单、我的的整体框架，删除 Project 逻辑，重点补商品编辑、订单详情、履约核销、售后和资金结果。

Web：

> 不重新设计 LiLiShop Manager 已有页面，仅新增合作协议和微信分账相关页面，并在商户详情、订单详情等既有页面中补大光路字段。

后续进入 Codex 原型修改时，应按本方案的页面批次逐批修改，不一次性重写两个小程序。
