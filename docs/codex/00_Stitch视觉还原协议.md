# 00｜Stitch 视觉还原协议

> 适用项目：大光路智慧社区数字化运营平台 V1.0 小程序  
> 适用终端：住户小程序、商户小程序  
> 适用阶段：所有使用 Codex 进行小程序页面开发、重构和视觉校准的阶段  
> 协议定位：规定“有 Stitch 母版时，Codex 应如何读取视觉输入、如何还原页面、如何验收视觉结果”。  
> 注意：本协议不定义业务规则，不替代 PRD，不替代 Design System，也不替代微信小程序工程规范。

---

# 1. 核心原则

页面开发统一采用以下四层输入：

```text
业务真源
PRD / 产品详细设计
        ↓
基础视觉规范
MiniApp Design System
        ↓
微信小程序实现规范
uni-app / 微信小程序布局、安全区、组件与工程规则
        ↓
页面视觉参考
Stitch screen.png（必要时辅以 code.html）
```

四层职责必须分开：

| 输入 | 决定内容 |
|---|---|
| PRD | 页面是什么业务、有哪些字段、状态、操作、权限和流程 |
| 页面实施清单 | 当前阶段是否开发、页面范围和入口 |
| Design System | 颜色、字体、间距、圆角、状态语义、公共组件视觉规则 |
| 微信小程序规范 | safe-area、胶囊区、TabBar、rpx/px、图片、滚动、固定底栏、uni-app 实现规则 |
| Stitch `screen.png` | 具体页面怎么排、模块顺序、几何结构、信息密度、视觉层次 |
| Stitch `code.html` | 辅助理解尺寸、padding、flex/grid、圆角和结构，不作为可复制代码 |

冲突时：

> **业务服从 PRD；页面范围服从实施清单；基础视觉服从 Design System；小程序实现服从微信小程序规范；具体页面构图优先参考 Stitch。**

---

# 2. Stitch 的定位

Stitch 不是业务真源。

Stitch 是：

> **页面视觉母版与页面类型参考。**

当某页面存在已经确认的 Stitch `screen.png` 时：

> `screen.png` 是该页面的视觉验收基准。

Codex 不得把“参考 Stitch”理解为：

> 只参考配色和大概模块，然后重新设计页面。

而应理解为：

> 在不违反 PRD、Design System 和微信小程序规范的前提下，尽量还原 Stitch 的页面构图、信息层级和视觉质感。

---

# 3. Stitch 参考等级

开发页面前，先根据《Stitch视觉母版映射表》判断视觉参考等级。

## L1｜直接对应页面

当前开发页面存在一张直接对应的 Stitch 母版。

例如：

```text
购物车
→ Stitch 购物车 screen.png
```

要求：

- 必须直接打开对应 `screen.png`；
- 页面整体结构应尽量还原；
- 可按需读取同目录 `code.html`；
- 不允许换成另一种页面结构。

## L2｜同类型参考页面

当前页面没有一一对应的 Stitch 页面，但已有相同页面类型母版。

例如：

```text
收货地址编辑
→ 参考“新增商品”的移动表单语言
```

要求：

- 从映射表确定 1 张主参考母版；
- 最多增加 1 张辅助参考母版；
- 只复用页面类型、组件和视觉语言；
- 业务字段必须来自当前 PRD；
- 禁止把参考母版的业务字段复制到当前页面。

## L3｜仅 Design System

没有合适 Stitch 母版。

要求：

- 按 Design System + 微信小程序规范生成；
- 优先复用现有公共组件；
- 不自行发明新的品牌视觉体系；
- 页面完成后判断是否形成新的通用页面类型，必要时再补 Stitch 母版。

---

# 4. 页面开发前的固定动作

开发任何正式页面前，Codex 必须依次执行：

```text
1. 读取 AGENTS.md
2. 读取当前阶段任务文件
3. 读取页面实施清单中的当前页面
4. 读取 PRD 对应章节
5. 读取 Design System 相关规则
6. 读取微信小程序规范相关规则
7. 查询 Stitch 母版映射
8. 打开必要的 screen.png
9. 必要时读取对应 code.html
10. 再开始编码
```

不得：

- 一次性遍历全部 Stitch；
- 一次性把所有 PRD 全文加载到当前页面上下文；
- 在没有打开对应视觉母版时直接凭印象开发有母版的页面。

# 5. 必须直接观察的视觉要素

查看 `screen.png` 时至少提取以下内容：

## 5.1 页面背景

默认页面主体背景：

```text
#F8F9FC
```

除非 Stitch 明确为沉浸式特殊场景，否则：

> **禁止默认整页纯白。**

标准层次：

```text
浅灰页面背景 #F8F9FC
        ↓
白色卡片 #FFFFFF
        ↓
轻边框 / 极轻阴影
```

推荐：

```text
卡片背景：#FFFFFF
边框：#E1E4E6，弱化使用
阴影：0 2px 8px rgba(27,77,83,0.04)
```

页面层级主要依靠：

- 浅灰背景；
- 白色卡片；
- 留白；
- 间距；
- 极轻阴影。

不要主要依靠重边框。

## 5.2 顶部结构

观察：

- 品牌栏是否独立；
- 页面标题是否独立；
- 副标题位置；
- 搜索框与标题关系；
- 微信胶囊预留；
- 是否存在当前项目/社区上下文。

不得为了复用 AppNavbar 擅自合并原型中独立的层级。

## 5.3 卡片

观察：

- 卡片宽度；
- 左右边距；
- 圆角；
- 内边距；
- 卡片之间距离；
- 卡片是否自然高度；
- 是否有嵌套卡片。

禁止因为复用 `BaseCard` 而制造固定高度和大量无意义空白。

## 5.4 Typography

观察：

- 页面标题；
- Section Title；
- Card Title；
- Body；
- Meta；
- Price。

以 Design System 字体 Token 为基础，同时匹配 Stitch 的视觉层级。

避免：

- 大量 700 字重；
- 页面所有标题都一样重；
- 为了“醒目”擅自放大字号。

## 5.5 图标

正式页面禁止：

- 汉字占位图标；
- emoji；
- 多套图标风格混用。

图标优先级：

1. 项目现有图标库；
2. 已有 iconfont / uni-icons；
3. 本地 SVG；
4. 必要时新增统一线性图标资源。

需要匹配 Stitch：

- 图标尺寸；
- 视觉重量；
- 图标容器；
- 浅色背景；
- 图标与文字的距离。

## 5.6 图片与素材

如果 Stitch 母版使用真实生活照片或真实商品图：

> Codex 不应随意替换为扁平插画。

没有最终业务素材时，可使用本地 Mock 图片，但要求：

- 图片类型与母版一致；
- 比例接近；
- 色调接近；
- 用于生活服务的页面优先真实感照片；
- 商品卡优先真实感商品图。

Mock 素材只用于视觉还原，不代表业务已经正式上线。

## 5.7 Bottom Tab

必须匹配当前端：

住户端：

```text
首页｜服务｜商城｜我的
```

商户端：

```text
工作台｜经营｜订单｜我的
```

视觉规则：

- 白色整体底栏；
- 轻分割线；
- 图标 + 文字；
- 激活使用主色；
- 未激活使用中性灰；
- 不把四个 Tab 做成四张独立边框卡片。

# 6. 页面几何结构还原要求

有直接 Stitch 母版时，以下内容原则上应保持一致：

- 页面模块顺序；
- 一行入口数量；
- 卡片组合关系；
- 主视觉位置；
- 搜索框位置；
- 图片与文本的左右/上下关系；
- Bottom Action 的位置；
- Bottom Tab 的位置；
- 页面信息密度；
- 主要留白比例。

允许因为微信小程序运行环境产生的合理差异：

- status bar；
- 微信胶囊；
- safe-area；
- 字体实际渲染；
- rpx 换算；
- 不同设备高度。

不允许以“小程序实现不同”为理由重新设计整个页面。

---

# 7. 组件化原则

组件化目标：

> 复用实现，不改变最终视觉。

正确：

```text
同一个 QuickEntryItem
支持不同页面的图标、背景、间距配置
```

错误：

```text
为了使用同一个 QuickEntryGrid
把所有页面强制做成一样的列数、卡片边框和固定高度
```

公共组件应该提供：

- Design Token；
- 合理默认值；
- 必要样式变体；
- Slot / Props；
- 页面级布局可配置性。

不要把 Stitch 某一页的业务内容写死进公共组件。

---

# 8. `code.html` 使用边界

可以参考：

- DOM 层级；
- flex / grid；
- padding / gap；
- 圆角；
- 卡片比例；
- 字号关系；
- 图片比例。

禁止复制：

- Tailwind class；
- Google Fonts；
- Material Symbols Web Font；
- 浏览器 hover；
- PC 响应式；
- 固定 viewport 高度；
- Web 专用 DOM。

最终必须转换为：

- Vue3；
- uni-app；
- `view / text / image / scroll-view`；
- 当前项目公共组件；
- 微信安全区；
- 当前主题 Token。

---

# 9. 业务未完成时的视觉处理

一个入口属于 P2-P5，业务尚未开发：

> **不代表首页/入口页要显示成开发占位 Demo。**

如果 Stitch 中该模块是完整展示卡片：

- 视觉仍按 Stitch 完整展示；
- 可使用合理 Mock 数据；
- Mock 放统一 Adapter；
- 点击后进入 `FeatureUnavailable` / “功能建设中”。

例如：

```text
首页 ServiceCard
可以展示完整服务图片、标题、说明、价格
↓
点击
↓
FeatureUnavailable
```

禁止为了表示未开发，把正式视觉全部替换为：

```text
大图标
“功能待设计”
“建设中”
```

除非该页面本身就是建设中状态页。

# 10. 页面视觉验收流程

每个存在 Stitch 母版的页面，完成编码后必须执行：

```text
运行页面
↓
获取当前页面截图
↓
与 Stitch screen.png 对照
↓
修正明显偏差
↓
再次检查
↓
才可以标记页面视觉完成
```

至少检查：

## 结构

- 模块顺序；
- 页面标题区；
- 容器数量；
- 是否多出不必要卡片。

## 几何

- 左右边距；
- 卡片宽度；
- 卡片间距；
- 图片比例；
- 一行元素数量；
- 是否出现大量无意义空白。

## 视觉

- 页面浅灰背景；
- 白色卡片层次；
- 字体大小和字重；
- 主色；
- Accent；
- 图标；
- 图片风格；
- Bottom Tab。

## 状态

- active / disabled / pending / success；
- 不能只靠颜色；
- 业务状态文案服从 PRD。

# 11. 截图验收要求

如果 Codex 当前环境支持：

- 浏览器预览；
- H5 预览；
- 小程序模拟器截图；
- 自动化截图；

应尽量生成当前页面截图。

建议宽度：

```text
约 375–390px 逻辑宽度
```

截图保存到临时验收目录，例如：

```text
.tmp/visual-review/
```

临时截图不必提交 Git。

如果 Codex 无法截图：

> 必须明确汇报“代码已完成，待人工视觉验收”，不得直接声明“已完全还原 Stitch”。

用户人工提供截图后，在当前 Task 继续完成视觉修正。

---

# 12. Stitch 图片如何提供给 Codex

优先方式：

```text
仓库中已有
docs/stitch/.../screen.png
```

Codex 直接打开当前页面对应图片。

如果当前 Codex 客户端无法可靠读取仓库图片：

> 在当前 Task 中直接附加该页面对应的 Stitch `screen.png`。

每个页面原则上只提供：

- 1 张直接对应母版；

或者没有直接母版时：

- 1 张主参考；
- 最多 1 张辅助参考。

不要一次向一个页面任务提供大量无关截图。

---

# 13. 页面开发完成条件

有 Stitch 母版的页面同时满足以下条件才算完成：

## 业务

- 字段符合 PRD；
- 状态符合 PRD；
- 操作符合 PRD；
- 权限边界正确。

## 小程序实现

- safe-area 正确；
- 微信胶囊不遮挡；
- 滚动正常；
- 固定栏不遮挡内容；
- 两个小程序端级导航正确；
- 无 Web 专用依赖。

## 视觉

- 第一眼与 Stitch 属于同一套页面；
- 页面背景、卡片层次正确；
- 模块顺序一致；
- 图标正式；
- 图片类型接近；
- 信息密度接近；
- 无明显自行重设计。

## 工程

- 复用公共组件；
- 不复制 Web 代码；
- 无第二套 Theme；
- Mock 集中管理。

# 14. 双小程序约束

住户端与商户端是：

> **两个独立微信小程序。**

必须分别：

- 构建；
- 发布；
- 配置 AppID；
- 拥有独立 App Shell；
- 拥有独立 pages；
- 拥有独立 TabBar。

允许共享：

- Design Token；
- UI 公共组件；
- Request；
- API Type；
- 工具；
- Project 公共模型；
- 通用业务组件。

禁止：

> 一个小程序通过运行时角色切换 Resident / Merchant 一级导航。

视觉验收时必须确认页面属于正确小程序。

# 15. Codex 每个页面的执行模板

当阶段任务要求实现某页面时，执行：

```text
【业务】
读取 PRD 当前页面章节

【范围】
读取页面实施清单当前页面

【基础视觉】
读取 MiniApp Design System

【小程序实现】
读取微信小程序前端实现规范

【Stitch】
根据映射表确定：
L1 直接母版 / L2 类型母版 / L3 无母版

如 L1/L2：
直接打开必要 screen.png
必要时读取 code.html

【开发】
复用已有组件实现

【验收】
运行并截图
对比 Stitch
修正明显差异
测试业务状态
```

# 16. 阶段任务中的统一引用语句

后续所有 `docs/codex/XX_*.md` 阶段文件不需要重复本协议全文。

统一加入：

> 本阶段所有页面开发必须遵守 `docs/codex/00_Stitch视觉还原协议.md`。  
> 页面存在 Stitch 母版或同类型参考母版时，必须在编码前直接查看对应 `screen.png`，完成后执行视觉对照验收。  
> 未完成截图对照的页面，不得标记为视觉完成。

# 17. 最终原则

今后页面开发不是：

```text
PRD + Design System
→ Codex 自己设计页面
```

而是：

```text
PRD
+ 页面实施清单
+ 基础 Design System
+ 微信小程序实现规范
+ 必要 Stitch screen.png
→ Codex 实现
→ 当前页面截图
→ 对照修正
→ 完成
```

其中：

> **PRD 决定“是什么”；Stitch 决定“长什么样”；Design System 决定“统一成什么体系”；微信小程序规范决定“如何正确落地”；Codex 负责“实现并验证”。**
