## 4. LiLiShop 映射与数据模型

独立 `AfterSaleRecord` 作为售后事实，不将 Order 上两个状态字段当成完整售后。身份保留 `id/sn/tradeId/tradeSn/orderId/orderSn/orderItemSn/storeId/operatorId/memberId/productId/skuId`，对接时 `productId` 对应 Goods、`skuId` 对应 GoodsSku，售后数量落到 OrderItem/SKU。

| 原型字段 | 对接语义 |
|---|---|
| `serviceType` | `RETURN_MONEY` 退款、`RETURN_GOODS` 退货退款 |
| `serviceStatus` | `APPLY/PASS/REFUSE/BUYER_RETURN/SELLER_CONFIRM/BUYER_CANCEL/WAIT_REFUND/COMPLETE` |
| `quantity/item` | 本次数量及购买时商品/SKU/数量/图片/单价快照 |
| `reason/problemDesc/images` | 配置申请原因、最多 500 字、最多 6 图 |
| `maxRefundAmount/applyRefundAmount/actualRefundAmount` | 报价上限/申请/实际退款，均为整数分 |
| `merchantAuditRemark` | 商户拒绝原因，不允许商户改变申请金额 |
| `mLogisticsCode/mLogisticsName/mLogisticsNo/mDeliverTime` | 居民退货物流公司、单号、提交时间 |
| `returnMethod/returnRemark/returnReceivedAt` | 现场退回或自行快递、备注、实际确认收货时间 |
| `refundStatus/refundTransactionNo/refundAt` | 独立退款维度，对接 Payment/RefundLog 的预留 |
| `stockRestored/restoreStockOnRefund` | 库存恢复幂等标记/申请时是否未交付 |
| `profitSharingReturnRequired/fundAdjustmentStatus` | 需平台资金回退/调整的预留，不执行资金回退 |
| `timeline[]` | 售后独立事件及时间/操作人，未混入订单履约 timeline |

`ResidentAfterSaleView` 与 `MerchantAfterSaleView` 分别返回展示状态、下一步和可用操作。居民 DTO 删除库存内部标记及分账回退/资金调整字段；相关 Order/Trade 居民 DTO 同样删除本轮资金预留字段。

## 5. 申请资格、数量与金额

Service/Adapter 返回 `allowRefund/allowReturnGoods/reason`，页面不推算完整订单状态机。未支付/已关闭拒绝；未交付仅退款；配送中/已发货/已送达/已核销/已完成允许配置范围内退款或退货。`afterSaleExpiresAt`、`afterSaleEnabled` 为 Mock 配置，页面没有写死七天。

可申请数量 = 购买数量 − 已完成有效售后数量 − 活动售后占用数量。拒绝和取消释放占用；已有活动售后但仍有剩余数量，可以另申请。超购买量、超剩余量、零/小数数量、无剩余金额均拒绝。已完成售后不允许对同一数量重复退款。

Adapter 按商品实付分摊并扣除已申请/已退金额，排除配送费/运费，返回本次数量上限；页面只格式化与校验输入。计算保持整数分，尾差计入剩余数量最后一次申请，累计不超过商品实付。提交时再次校验数量、金额、类型、原因、描述和图片。

幂等键按居民作用域保留，相同键只返回原记录；页面提交 busy/quoting 防止重复点击及报价刷新中提交。

## 6. 退款流程

`居民申请 APPLY → 商户同意 → WAIT_REFUND（无退款） → 平台 Mock 处理中/结果 → COMPLETE + 退款成功`。

商户同意仅审核，实际退款金额初始 0，没有流水/到账时间。平台成功才写实际金额、退款时间、`MOCK-REFUND-*` 流水与平台事件。平台失败仍为 WAIT_REFUND，居民看到“退款异常，平台处理中”；只有平台模拟器可再次模拟 processing/success，居民页面没有微信退款重试按钮。COMPLETE 不再提供审核、取消或收货操作。

平台模拟器为单独 `platformRefundDemoService`，仅在商户详情折叠“原型演示（Mock）”区显示，明示平台角色并二次确认，不是普通商户主操作。普通商户售后 Service 不导出平台退款方法。当前原型没有真实平台登录/支付权限校验。

## 7. 拒绝、取消与退货

商户拒绝必须输入原因，500 字内，确认后为 REFUSE，居民可见原因；取消只允许未审核 APPLY，确认后 BUYER_CANCEL。两者解除履约限制并保留历史，可在规则允许时从订单重新申请。

`退货申请 APPLY → 同意 BUYER_RETURN → 居民提交退货 → 等待商户实际收货 → SELLER_CONFIRM 事件 → WAIT_REFUND → 平台退款 → COMPLETE`。

居民支持现场退回或自行快递。快递公司/编码和 5～40 位有效单号必填，备注最多 200 字。提交保留 BUYER_RETURN，通过 `mDeliverTime` 区分“等待退货/等待商家收货”，禁用重复提交。商户不能未收到就确认，页面明示“实际收到”并 Modal 确认；确认收货记录时间，不立即退款，不重复确认。

## 8. 商户和居民隔离

商户列表、详情、订单售后、同意、拒绝和收货均校验当前 `storeId` 与 `operatorId`。相同 Operator 不同 Store 仍隔离，猜测他店售后/订单 ID 直接拒绝。门店模拟切换复用第四批演示面板，未增加角色/Tab 切换。

居民售后资格、列表、详情、创建、取消和退货均校验 `memberId` 与关联订单归属。新增当前居民订单列表/详情归属校验；`member-other` 仅为 Adapter 自动测试上下文，没有居民角色切换 UI。售后权限为 Mock 业务验证，不代表真实鉴权上线。

## 9. 订单聚合与履约关系

每次售后变更从独立记录派生 Order 的 `afterSaleStatus/refundStatus/hasAfterSaleRecords/afterSaleSummary/refundedAmount/fulfillmentBlocked`。同时维护每个商品 `remainingFulfillmentQuantity`。

活动售后阻断所属子订单备货、发货、配送、核销和居民确认收货；拒绝/取消解除限制，不改变原履约状态。已完成订单保持“已完成 + 售后处理中”，不回退履约。已退完未交付商品的订单继续禁止履约；部分完成后可继续剩余数量，商户列表/详情和核销核对显示剩余数量。

同一 Trade 的兄弟 Store 子订单金额、状态、库存和履约不受影响。部分退款不关闭整单或整笔交易，不将退款成功冒充交易支付/履约状态。

## 10. 库存与分账回退预留

唯一恢复点选择“平台退款成功”：未交付退款成功恢复对应售后数量；退货实际收货后也只在平台成功时恢复。商户确认退货时不恢复，平台重复结果不恢复第二次；已实际交付且不退货的仅退款不补库存。库存写入现有商城 Mock 产品/SKU 源，保留 stockRestored 标记。

未分账订单的 `profitSharingEligibleAmount = paidAmount − 已成功退款金额`，工作台待分账汇总使用此金额。已分账或分账中订单模拟退款时标记 `profitSharingReturnRequired` 与 `待平台资金调整`，不改写为已执行分账回退。商户只看到退款金额与“资金调整处理中”，居民看不到资金回退字段。
