# 1. 规范职责与优先级

项目页面开发时，按以下顺序理解约束：

```text
PRD / 产品详细设计
        ↓
页面实施清单
        ↓
MiniApp Design System
        ↓
本微信小程序实现规范
        ↓
Stitch screen.png / code.html
        ↓
现有 uni-app / yudao-mall-uniapp 能力
```

各文件职责：

| 输入 | 负责内容 |
|---|---|
| PRD | 业务对象、字段、状态、流程、权限、规则 |
| 页面实施清单 | 当前是否开发、页面范围、入口 |
| Design System | 品牌色、字体、间距、圆角、组件视觉语言 |
| 本规范 | 微信小程序 / uni-app 的导航、安全区、缩放、滚动、触控、资源与工程落地 |
| Stitch | 具体页面布局、模块顺序、几何结构、信息密度 |
| 现有代码 | 成熟商城能力、请求、登录、状态管理等技术复用 |

冲突规则：

> 业务服从 PRD；视觉基线服从 Design System；微信平台适配服从本规范；具体页面构图优先参考 Stitch。

# 2. 双小程序工程边界

住户端与商户端是**两个独立微信小程序**，不是同一小程序中的角色切换模式。

必须分别拥有：

- 独立 App Shell；
- 独立 `pages.json` / 页面路由；
- 独立 TabBar；
- 独立 `manifest` / AppID 配置；
- 独立构建与发布产物；
- 独立一级首页和登录入口。

住户端固定一级导航：

```text
首页｜服务｜商城｜我的
```

商户端固定一级导航：

```text
工作台｜经营｜订单｜我的
```

禁止：

> 一个小程序登录后根据角色动态切换 Resident / Merchant 一级导航。

允许共享：

- Design Token；
- UI 公共组件；
- Request / API Type；
- 上传与文件能力；
- 工具函数；
- Project 公共模型；
- 通用状态组件；
- 通用业务组件。

# 3. 390px 响应式基准

本项目统一采用：

> **390px 响应式设计基准。**

依据微信官方指南：

- 可采用 375px 固定基准；
- 或采用 390px 响应式基准；
- 不建议在同一项目混用两种适配逻辑。

本项目选择 390px，是因为当前 Stitch 母版本身接近 390px 逻辑宽度。

项目要求：

- 页面结构按 390px 基准理解；
- 不固定死真实设备宽度；
- 左右 gutter 保持 Design System 统一值；
- 窄屏允许必要换行和紧凑处理；
- 宽屏不简单等比放大全部卡片；
- 禁止同时使用“375 固定缩放”和“390 响应式”两套规则。

# 4. 微信官方菜单、状态栏与自定义导航

微信会在页面右上角提供官方小程序菜单。

所有自定义顶部区域必须：

- 预留官方胶囊区域；
- 不覆盖官方菜单；
- 不在菜单附近堆叠高频交互；
- 保证返回按钮、标题、搜索等不会与官方菜单冲突。

实现要求：

- 不写死状态栏高度；
- 使用微信运行环境提供的系统信息 / 菜单位置信息计算安全区域；
- 自定义导航栏需要单独验证 Android / iOS；
- 次级页面必须存在清晰返回路径；
- 不仿造微信官方菜单。

对 Stitch 的处理：

> Stitch 顶部结构决定页面层级，但真正落地时必须让位于微信官方菜单安全区。

# 5. TabBar 与页面内 Tab

## 5.1 一级 TabBar

仅一级首页体系使用底部 TabBar。

住户：

```text
首页｜服务｜商城｜我的
```

商户：

```text
工作台｜经营｜订单｜我的
```

要求：

- 四项平均分布；
- 图标 + 文案居中；
- 激活态使用项目品牌主色；
- 未激活使用中性灰；
- 自定义 TabBar 必须单独适配字体缩放；
- 不在二级详情、表单、结果页重复显示一级 TabBar。

## 5.2 页面内 Tab

页面内 Tab：

- 数量 2–5；
- 推荐不超过 4；
- 一个页面只使用一组页面内 Tab；
- 位置在项目内保持一致；
- 文案清晰；
- 不与一级 TabBar 混淆。

# 6. 页面重点与流程

每个页面必须有一个明确主任务。

要求：

- 首屏能快速判断“当前在哪、现在要做什么”；
- 流程页不插入与当前目标无关的内容；
- 详情页明确当前状态与下一步；
- 结果页明确成功/失败以及下一步；
- 异常状态必须有返回、重试、修改或联系客服等恢复路径。

禁止：

- 在交易流程里插广告、推荐、活动；
- 在审核、售后、支付等关键流程里加入无关运营内容；
- 为了“页面丰富”增加与当前决策无关的信息。

# 7. 页面背景与卡片层级

项目统一页面主体背景：

```text
#F8F9FC
```

默认卡片：

```text
#FFFFFF
```

分组浅底：

```text
#F2F4F6
```

卡片层级主要依靠：

- 浅灰页面背景；
- 白色卡片；
- 留白；
- 间距；
- 极轻边界 / 阴影。

禁止：

- 默认整页纯白；
- 用大量粗边框替代页面层次；
- 为了复用 `BaseCard` 固定卡片高度；
- 制造无意义大面积空白。

这一条属于本项目 Design System 的落地约束，不是微信官方色彩要求。

# 8. 字体与大字体适配

使用系统字体。

项目默认字号以 Design System 为准，同时支持微信字体大小设置。

依据官方指南，应读取微信提供的字体大小相关参数，优先使用当前维护的系统信息接口。

自定义组件适配原则：

1. 文本随微信字体缩放；
2. 图标、按钮等必要元素根据字体缩放合理放大；
3. 元素之间固定布局间距尽量保持稳定；
4. 达到宽度极限时允许换行；
5. 核心信息不得截断；
6. 自定义导航栏、自定义 TabBar 必须单独测试大字体；
7. 原生导航和原生 TabBar 优先使用平台能力。

项目特别要求：

- 核心正文默认不低于 15px；
- 不通过大量 12px 小字提升信息密度；
- 大字体模式下优先保证内容完整和任务完成。

---

# 9. 触控热区

微信官方指南强调移动端点击精度和热区。

本项目统一要求：

- 常规主要点击目标尽量不小于 44×44px 逻辑尺寸；
- 小图标、文字链接周围扩大点击热区；
- 图标 + 文案指向同一动作时使用连续完整热区；
- 整张卡片指向同一详情时，整卡可点击；
- 不让多个小操作按钮挤在同一行；
- 特殊小元素也必须保证足够热区。

不要只看图标的视觉尺寸，应单独考虑可点击区域。

---

# 10. 输入与表单

优先减少键盘输入。

优先使用：

- 微信授权能力；
- 扫码；
- 拍照；
- 定位；
- 地址选择；
- 历史记录；
- Picker / Selector；
- Bottom Sheet；
- 合理默认值。

不得不输入时：

- 给出明确 label；
- 提供合理 keyboard type；
- 避免输入项连续堆叠；
- 长表单按业务分组；
- 分步骤表单可保存草稿；
- 错误在字段原位反馈；
- 页面顶部可汇总错误；
- 键盘弹出后不能遮挡当前字段和主操作。

Stitch 中的表单视觉可以还原，但不能复制 Web input 行为。

---

# 11. 加载与反馈

优先使用微信原生下拉刷新和平台能力。

## 11.1 加载

优先：

> 局部加载。

慎用全屏模态加载。

同一页面：

> 不同时出现多个加载动画。

加载较长时：

- 提供进度；
- 必要时允许取消；
- 保持动画，避免用户误认为卡死。

## 11.2 成功反馈

轻量成功：

- Toast / 轻提示；
- 不打断任务。

流程结束：

- 使用 ResultState / 结果页；
- 明确下一步。

## 11.3 错误反馈

错误不得只用一闪而过的 Toast。

必须：

- 说明原因；
- 告知恢复方式；
- 表单错误定位到具体字段；
- 网络错误提供重试；
- 权限不足说明如何处理。

# 12. 页面状态

正式页面至少考虑：

- loading；
- empty；
- error；
- network-error；
- disabled；
- no-permission；
- business-unavailable。

提交型页面增加：

- submitting；
- duplicate-submit；
- business-limited。

要求：

> 异常状态必须“有路可退”。

禁止只实现正常有数据状态。

---

# 13. 页面滚动

页面主滚动优先使用小程序标准页面滚动。

只有明确需要局部独立滚动时才使用 `scroll-view`。

禁止：

- 多层纵向滚动嵌套；
- 主页面和内部列表同时抢滚动；
- 固定高度容器导致内容被裁掉；
- 用 `100vh` 简单覆盖状态栏、TabBar 和 safe-area。

长列表：

- 复用项目成熟列表能力；
- 支持分页 / 加载更多；
- 避免一次渲染大量复杂节点；
- 图片懒加载。

---

# 14. Bottom Action 与安全区

固定底部操作栏必须：

- 不遮挡页面内容；
- 预留 `safe-area-inset-bottom`；
- 滚动内容增加足够 bottom padding；
- 主次按钮清楚；
- 尽量不同时放超过两个主要动作。

典型：

```text
取消 / 次操作     提交 / 主操作
```

二级页面固定 Bottom Action 与一级 TabBar 不应同时存在。

---

# 15. 图标

正式图标优先级：

1. 项目现有图标库；
2. 统一 iconfont / uni-icons；
3. 本地 SVG；
4. 新增统一线性 SVG。

禁止：

- 汉字占位；
- emoji；
- Material Symbols Web Font；
- 多套不同视觉风格混用。

图标必须配合足够热区。

Stitch 图标只作为视觉参考，不复制 Web 字体实现。

---

# 16. 图片与资源

图片处理原则：

- `image` 明确 `mode`；
- 商品图 / 服务图保持统一比例；
- 头像、Banner、商品图使用不同预设；
- 列表图片懒加载；
- 失败时提供占位图；
- 避免大图原尺寸直接加载；
- 静态 Mock 素材集中管理。

如果 Stitch 使用真实生活照片：

> 不应随意替换为扁平插画。

没有正式素材时允许使用真实感 Mock 图片，保证：

- 类型接近；
- 比例接近；
- 色调与页面匹配。

---

# 17. 原生能力优先

优先采用微信原生或标准能力：

- 页面返回；
- 下拉刷新；
- 扫码；
- 图片选择 / 拍照；
- 定位；
- 授权；
- 网络状态；
- 分享；
- Picker；
- 系统信息。

不要为了视觉一致重新实现微信已有成熟交互。

如果自定义：

> 必须保证与官方控件可区分、全局一致，并满足可访问性和大字体适配。

# 18. Stitch → uni-app 转换

Stitch `screen.png`：

> 页面视觉验收基准。

Stitch `code.html`：

> 辅助理解布局，不是代码模板。

可参考：

- 模块顺序；
- padding；
- gap；
- flex / grid；
- 圆角；
- 图片比例；
- 字体层级。

禁止复制：

- Tailwind；
- Web DOM；
- Google Fonts；
- Material Web Icons；
- hover；
- desktop media query；
- 浏览器固定 viewport；
- Web-only JS。

必须转换为：

- Vue 3；
- uni-app；
- 小程序组件；
- 项目公共组件；
- 项目 Design Token；
- 微信安全区。

# 19. Stitch 视觉还原执行规则

所有存在 Stitch 母版或参考母版的页面必须遵守：

`docs/codex/00_Stitch视觉还原协议.md`

页面开发前：

1. 查询映射表；
2. 判断 L1 / L2 / L3；
3. L1 / L2 直接打开必要 `screen.png`；
4. 按需读取 `code.html`。

开发后：

1. 运行页面；
2. 获取当前页面截图；
3. 与 Stitch 对照；
4. 修正明显差异；
5. 再标记视觉完成。

# 20. Mock 与未开发业务

业务尚未开发，不等于入口页面必须呈现开发 Demo。

允许：

- 首页、服务页使用完整 Mock 服务卡；
- 商城使用合理商品 Mock；
- 点击未开发 P2-P5 功能进入 `FeatureUnavailable`。

Mock 要求：

- 集中在 Adapter / Mock 层；
- 页面不散落硬编码；
- 不创造正式业务规则；
- 不伪装成真实后端接口。

住户端：

```text

currentMember
```

商户端：


# 22. 性能与页面体量

优先：

- 复用成熟组件；
- 图片压缩；
- 懒加载；
- 分页；
- 避免巨型页面组件；
- 避免重复请求；
- 页面返回后按需刷新；
- 大列表减少复杂节点和重复计算。

如果两个独立小程序体量变大：

- 分别规划各自分包；
- 不因为共享代码让两个端打包全部对方业务页面。

# 23. 官方指南与项目品牌的边界

微信官方指南提供平台通用体验原则。

大光路项目允许叠加品牌设计，但必须满足：

- 官方菜单安全区不被破坏；
- 导航清楚；
- 状态和风险明确；
- 触控可用；
- 大字体可用；
- 系统反馈清楚；
- 不因为品牌色影响可用性。

项目品牌主色：

```text
#1B4D53
```

用于项目自身：

- 主 CTA；
- Tab 激活态；
- 选中态；
- 品牌强调。

风险、错误继续使用明确错误色。

微信原生系统控件：

> 保持其平台原生行为和可识别性，不强行品牌化。

# 24. 页面完成前检查

每个正式页面至少检查：

## 页面任务

- 主任务是否明确？
- 是否存在无关干扰？

## 导航

- 当前在哪？
- 可以去哪？
- 如何返回？
- 官方菜单是否安全？

## 微信适配

- safe-area 是否正确？
- 大字体是否可用？
- TabBar / 自定义导航是否适配？
- 键盘是否遮挡？

## 反馈

- loading？
- empty？
- error？
- network error？
- 成功/失败下一步？

## 触控

- 主要热区够大？
- 图标与文字是否连续点击？
- 是否存在小按钮拥挤？

## Stitch

- 是否直接查看了对应 screen.png？
- 页面背景 / 卡片 / 间距 / 图片 / 图标是否接近？
- 是否实际截图对比？

# 25. Codex 阶段交付说明

每阶段完成时至少说明：

1. 使用了哪些原生微信能力；

3. 大字体适配方式；
4. loading / empty / error 覆盖情况；

# 27. 最终原则

项目小程序开发统一遵循：

```text
官方微信设计原则
```
